# 2026-04-13 开发进度归档

## 本轮完成改动

### 1. GUI 代码结构完成中等拆分
- `src/GUI.py` 保留为启动入口。
- GUI 主体已拆分为 `src/gui/runtime.py`、`src/gui/widgets.py`、`src/gui/presentation.py`、`src/gui/window.py`。
- 作用：
  - 把线程、显示控件、展示映射、主窗口编排从单文件中拆开。
  - 后续继续调显示链路、事件区布局和性能热点时，不需要再在一个超大文件里来回修改。

### 2. 推理设备与视频工作分辨率已接入 GUI
- 已支持 `自动 / CPU / GPU` 推理设备选择。
- 已支持视频文件模式的 `720p / 1080p` 工作分辨率档位。
- 作用：
  - 能在不同机器上明确控制 CPU/GPU 推理路径。
  - 对高分辨率视频可先缩到工作分辨率后再检测，减轻解码后到推理前的 CPU 压力。

### 3. 显示链路已改为“最新帧优先”
- 检测线程不再把每一帧大图直接塞给主线程显示。
- 主线程改为定时拉取最新预览帧，允许丢弃过时帧。
- 补齐了 `decode / model / analysis / draw / preview / present` 统计口径，并区分：
  - `显示 FPS`
  - `处理 FPS`
  - `模型 FPS`
- 作用：
  - 修复了此前“模型很快但显示很慢”的核心链路问题。
  - 让 GUI 刷新速度不再反向拖慢检测线程。

### 4. 乱码与旧逻辑分叉问题已清理
- 预警与状态文本乱码已修复。
- `DetectionThread.run()` 当前主路径已统一，旧分叉逻辑不再继续影响现行行为。
- 作用：
  - 避免 Windows 下字体/编码兼容问题继续污染事件栏。
  - 后续调试时性能结论更可靠，不会再被历史分支干扰。

### 5. 本轮新增：信息区重排与结构化预警
- 左侧 KPI 改为贴顶紧凑单列，宽度收口到更协调的固定值。
- 底部信息区由两栏改为三栏：
  - `分类统计`
  - `当前预警`
  - `事件流水`
- `warning_update` 已改为结构化载荷：
  - `active_items`
  - `timeline_items`
- 作用：
  - 不再让 UI 从中文句子里反向解析预警内容。
  - 相同空间内能展示更多有效数据，尤其是把“当前活跃告警”和“历史变化记录”拆开后，信息利用率明显更高。

## 每项改动解决的问题

| 改动 | 解决的问题 |
|------|------------|
| GUI 拆分为 `runtime/widgets/presentation/window` | 降低 `src/GUI.py` 单文件耦合度，便于后续继续调性能和界面 |
| 推理设备选择 | 避免设备路径不透明，便于对比 CPU / GPU 推理表现 |
| 视频工作分辨率档位 | 高分辨率视频检测时 CPU 压力过大、吞吐偏低 |
| 最新帧优先显示 | 模型 FPS 很高但显示 FPS 很低，GUI 成为反向瓶颈 |
| 统计口径细分 | 之前无法区分到底是解码、推理、绘制还是显示慢 |
| 乱码修复 | 预警与状态栏出现异常编码文本，影响可读性 |
| 当前预警 + 事件流水拆分 | 旧的单文本框同时承担“当前状态”和“历史记录”，信息混杂且空间利用差 |

## 当前性能基线

以下基线来自当前这轮稳定版运行截图与现有代码统计口径：

- 显示 FPS：约 `28.4`
- 处理 FPS：约 `23.7`
- 模型 FPS：约 `118.3`
- 平均步长：约 `1.32`
- `decode_ms`：约 `34.4 ms`
- `model_ms`：约 `8.5 ms`
- `analysis_ms`：约 `0.7 ms`
- `draw_ms`：约 `2.6 ms`
- `preview_ms`：约 `6.0 ms`
- `present_ms`：约 `2.3 ms`

当前结论：

- `模型 FPS` 已明显高于 `显示 FPS` 和 `处理 FPS`，说明模型推理不是主瓶颈。
- 现阶段决定吞吐上限的主要环节已经转为：
  1. `decode`
  2. `preview`
  3. 绘制与中文文字渲染

## 已知剩余瓶颈

### 1. 视频解码仍然最重
- 以当前基线看，`decode_ms` 仍是所有分项里最大的单项。
- 对未来 60FPS 视频，若继续沿用当前 OpenCV 读取链路，满帧实时显示不宜直接承诺。

### 2. 预览链路仍有冗余成本
- `preview_ms + present_ms` 仍会持续消耗主线程与图像转换成本。
- 分辨率越高、窗口越大，这部分成本越明显。

### 3. 文字与标签绘制在目标密集场景下会继续放大
- 当前 `draw_ms` 不算最高，但已经不是可以忽略的零成本。
- 尤其是中文标签、预警标记、轨迹线叠加多时，后续会更明显。

### 4. 高帧率场景下 UI 重复刷新仍有优化空间
- 统计、预警、事件流水在高刷新率下仍可能出现重复内容刷新。
- 这不一定是最大瓶颈，但会影响 60FPS 场景下的稳定度。

## 60FPS 视频准备评审结论

当前不建议直接承诺“60FPS 原视频一定能实时满帧显示”。原因不是模型，而是显示链路之外的系统性成本仍然存在，尤其是：

- 视频解码
- 预览缩放与 `QImage/QPixmap` 转换
- 多目标场景下的标签/文字绘制

结论优先级如下：

- `模型 FPS` 不是当前主瓶颈。
- 下一阶段优化优先级应固定为：
  - `decode`
  - `preview`
  - `draw / 文字渲染`
  - 其他分析逻辑
